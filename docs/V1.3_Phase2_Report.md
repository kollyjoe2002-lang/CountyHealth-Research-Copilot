## Registry structure

Registry version: `1.3.0-phase2.1`. Frozen dataclasses, tuples, frozensets and
read-only mappings hold 42 capability entries: 31 legacy executable data APIs,
3 disabled planned multidimensional capabilities, and 8 unsupported capabilities.
Exactly 11 of the existing data APIs are in the Research Assistant callable
allowlist. Seven catalog/status functions, four non-executing resolution
operations and three existing in-memory executor transforms are inventoried
separately. `aggregate_long_term_change` is explicitly unsupported because
the executor raises for that planned operation today.

Each capability records operation key, state, validation status, functions,
sources, available surfaces, comparison dimensions, geography modes,
restrictions, validator references, fixed filters and approved-pair policy.
Source restrictions distinguish burden/BMI, modeled prevalence and geography;
code year bounds are explicitly not data-availability guarantees.
Legacy validation status records existing validator coverage and does not
claim that warehouse-dependent validators freshly passed here.

`sex_age`, `sex_rurality` and `age_rurality` have no functions or execution
surfaces and remain non-executable. Unsupported forecasting, causal inference,
hypothesis testing, arbitrary intersections, composite metrics, PLACES
subgroup inference and unapproved concept pairs also remain unavailable.

Approved pairs are exactly DIABETES/976, STROKE/494 and CASTHMA/515.
The existing resolver constant and its dict/set API are unchanged; no alias
is needed for this passive checkpoint. An AST-based permanent validator
requires exact parity with the immutable canonical registry definition.
The registry notes that direct deterministic APIs do not independently apply
the semantic resolver's pair guard; Phase 2 does not change that behavior.

## Evidence structure and attribution boundary

`EvidenceSemantics` carries explicit dataset/version, concept, population,
unit, adjustment, observation/release years, interval type/level, provenance
and attribution. Its source-specific frozen contracts are:

- `IHMEYLLSemantics`: fixed YLL/rate role and IHME uncertainty intervals;
  attribution defaults to unknown/provenance-pending, never High BMI.
- `PLACESPrevalenceSemantics`: modeled prevalence in Percent; crude or
  age-adjusted; confidence intervals; separate measurement/release years
  and carry-forward status; risk attribution not applicable.
- `RUCCSemantics`: geographic classification, Category unit, classification
  year 2023, no health observation year or health-outcome interval.
- `CrossSourceSemantics`: separate IHME/PLACES items, optionally RUCC,
  geography basis, explicit same-year/contextual alignment, approved pair
  validation and descriptive interpretation. No composite metric field.

`Attribution` has unknown, verified and not-applicable states. A verified
attribution requires a nonempty label and immutable provenance references
matching the evidence dataset/version; unknown versions cannot authorize
verified attribution. `ProvenanceReference` identifies the dataset, version,
reference and verification note. References are attestations supplied by a
future verified import layer: merely constructing one is not independent
verification of an external document. No actual warehouse attribution has
been verified in this checkpoint. Positive validator examples are explicitly
synthetic attestations and establish no real High BMI attribution.

`semantic_claim_label` accepts controlled claim kinds. Attribution-dependent
labels fail when attribution is unknown, including when an attribution
requirement accompanies a generic claim kind. Verified attribution permits
only its exact label. PLACES cannot produce YLL/burden labels; RUCC cannot
produce health-outcome labels. These are source labels, not free-text report
validation or numerical epidemiological results. They are deliberately not
connected to the legacy report pipeline yet; no claim is made that Phase 2
retroactively changes existing report language.

## Gates still blocked

Fresh attempts confirmed missing analytical DuckDB for PLACES semantic,
PLACES-IHME semantic, rurality semantic, disparity semantic, legacy concept
compatibility, evidence-language guardrails, semantic entailment and all 12
children of the deterministic PLACES-IHME suite. Missing API credentials
block semantic full-chain, stress matrix, live parser and AI entailment judge.
The deterministic suite was invoked with `PYTHONPATH=.` for child imports.
All these attempts exited nonzero and are classified as blocked, not green.
The new self-contained concept-pair checks do not substitute for the legacy
warehouse-backed concept-compatibility suite. Full end-to-end legacy behavior
cannot be certified until development warehouse/API prerequisites exist.

Phase 2 local checks and runnable legacy gates pass. No new capability is
activated; parser, planner, resolver, executor, reporting, SQL and public
Streamlit behavior remain unchanged. Stop for review before Phase 3.
