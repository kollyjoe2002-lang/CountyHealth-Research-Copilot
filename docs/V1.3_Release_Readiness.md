# EpiCounty V1.3 release-readiness assessment

**Decision: NOT RELEASE READY.**

This is a local development/release-candidate assessment, not a production
release. The actual analytical warehouse was not supplied and live API credentials
are unavailable. Required warehouse, semantic-model, end-to-end and real-scale
performance gates therefore remain BLOCKED. Passing structural fixtures does not
remove those blockers. No production deployment or capability activation occurs.

UNKNOWN IHME attribution/unit scale is **not by itself** the reason for rejecting
the release. Safe presentation can withhold unsupported claims. If all required
legacy/data/model/performance gates pass in a suitable environment while the new
capabilities remain disabled, the supported decision is RELEASE READY WITH NEW
MULTIDIMENSIONAL CAPABILITIES STILL DISABLED. Neither that decision nor RELEASE
READY is justified by the current evidence.

## Architecture and researcher-facing changes

The canonical architecture remains conversation → semantic parser → typed
request → capability policy → canonical resolution → availability validation →
plan → allowlisted deterministic executor → evidence → grounded interpretation →
entailment → presentation. No second analytical pathway is introduced.

V1.3 provides immutable capability/evidence/query contracts, isolated deterministic
multidimensional analytics with coverage diagnostics, guarded semantic integration,
capability-aware clarification/fallback and bounded research intent. Streamlit
selects human-readable concepts/counties and observed eligible years; identifiers
are optional provenance outputs. Source metrics and interval types remain
separate. Cross-source relationships remain exactly DIABETES↔976, STROKE↔494,
CASTHMA↔515; no CHD/IHD or cancer pair is inferred.

Phase 8 adds explicit real-data activation auditing, complete gate inventory,
registry-generated capability documentation and fail-closed release classification.
It also fixes genuine provenance/privacy defects found during inspection:

- Legacy County Profile, Trend Finder and Disparity Finder no longer assert
  high-BMI attribution in public headings/captions; they disclose unknown source
  semantics. Analytical SQL and result formulas are unchanged.
- Public report/export/feedback errors no longer interpolate raw service errors.
  Legacy lookup failures render controlled infrastructure messages. Public stack
  traces/host paths are suppressed with the Streamlit client configuration.
- The current researcher request remains visible beside the latest exchange,
  anchored in the canonical typed outcome rather than reconstructed from chat.
  No display transcript or additional analytical state is added.

## Provenance determination

Inspected repository evidence:

- `database/schema.sql`: raw burden rows contain measure/metric IDs and names,
  demographic/cause/geographic fields, values/bounds, `source_file` and
  `imported_at`; no attribution field or verified rate-denominator metadata.
- `scripts/import/import_file.py`: identifies BURDEN/PAF/BMI families by filename,
  casts CSV columns, retains source basename/import timestamp and records SUCCESS
  in the import log. It does not import a verified risk-attribution descriptor,
  publisher dataset/version identity, unit scale or source checksum.
- `docs/ihme_file_inventory.csv`: filename-derived family/sex/year/release-date
  inventory. BMI tokens and dates in these filenames cannot verify attribution
  or bind a publisher release to the absent warehouse.
- Legacy README/report wording and historical release documentation are not
  independent scientific provenance. Historical deployment/backup records also
  do not establish current production state or fresh backup integrity.

**Attribution: UNKNOWN. Rate unit/scale: UNKNOWN. Publisher dataset/version and
actual warehouse import lineage: unverified.** No speculative provenance mapping
or stronger evidence contract is introduced.

The permanent lineage audit checks raw source-file/import timestamps against
unique SUCCESS/BURDEN import-log entries when those tables are explicitly supplied.
That proves linkage integrity only; it cannot transform filename classification
into scientific source/risk/unit verification. The audit never exposes source
paths in the public UI. Attribution-specific public claims remain disabled or
withheld. IHME uncertainty bounds, PLACES confidence intervals and RUCC geographic
classification retain distinct roles. Valid zero estimates remain observations;
absence never implies suppression.

## Permanent activation validator

`validate_multidimensional_activation.py` accepts an **explicit** development
warehouse path and opens it read-only. With no path it returns BLOCKED and performs
no production discovery/download. A known synthetic fixture marker prohibits a
real-data pass. Structural-test scope is intrinsically non-activating even if all
sample checks pass. No public fixture guard is exposed. Explicit audit/catalog/multidimensional
readers disable DuckDB external file/network access; supplied warehouse views
may not silently fetch other datasets.

The default sample profile includes IHD and Stroke, type 2 diabetes if catalogued,
years 2000/2010/2019, ages 40–44/60–64/80–84 and the standardized basis where
required. Operators can explicitly expand years/age labels. Missing optional
diabetes is reported, never mapped to a different condition. Missing required
causes/strata, invalid/nonfinite estimates/bounds, duplicate keys and empty coverage
fail sampled checks. The validator executes the original deterministic APIs on
both sex/age orientations, both fixed-sex summaries, fixed-age Both-sexes/Total-race
summaries and demographic comparisons within each validated RUCC group.

It records candidate/eligible/available/paired/excluded counties, missing RUCC,
per-group coverage, source missingness and result counts. Global duplicate RUCC
keys/fixed-year checks affect only rural capabilities. Triple intersections stay
rejected. Duplicate records are not hidden through aggregation/deduplication.

Coverage acceptance has no fabricated production default. Explicit county and
paired/rural percentage thresholds plus a scientific review reference are
required for a data-gate recommendation. These thresholds are a reviewed policy,
not inferred from fixture success. Read-only file metadata is checked before/after;
this is not falsely described as a full cryptographic source-identity audit.
A caller-supplied actual-development path is an operator assertion; the program
cannot authenticate a publisher dataset from an unmarked file alone.

## Performance findings

No actual warehouse query durations, real scan counts, production memory use or
Streamlit refresh overhead could be measured here. No implementation is optimized
on fixture timing evidence. The permanent audit records each operation's elapsed
time, returned observation/result counts and process peak RSS (where the platform
supports it), plus three uncached executions of the exact UI catalog refresh,
including connection overhead. Peak RSS is explicitly process-lifetime, not a
per-query allocation delta. Physical source rows read/full scan plans are not
invented where instrumentation is absent.

Code inspection identifies measurement targets: dense county × stratum × year
result objects and repeated DISTINCT catalog/year reads during Streamlit reruns.
These are potential costs, not demonstrated production regressions. Canonical analytical/catalog readers share one read-only, external-access-disabled
connection policy, including a test with simultaneous open readers. The shared
catalog projection was extracted solely to benchmark the same implementation
with an explicit read-only path; refresh/caching policy is unchanged.

## Known limitations, prerequisites and rollback

Actual source identity/version/units/attribution, production-scale cross-products,
exact cause/year availability, county/RUCC coverage, live semantic/entailment quality,
real performance and warehouse-backed UI behavior remain unverified. New validators
are necessary safeguards, not substitutes for these measurements. Future activation
must bind registry, policy, resolver, executor and public summaries together and
validate the intended envelope beyond any one representative sample.

The [exact conditional deployment/rollback plan](V1.3_Deployment_Plan.md) includes
verified production variables, read-only compatibility, runtime/API checks, writer
freeze, independently verified backup, clean fast-forward, systemd restart,
loopback/HTTPS health, page/semantic smoke tests, telemetry/feedback checks and
code-only rollback. It deliberately stops where host-specific facts or approvals
are missing. No AWS, SSM, systemd, Nginx or production commands were executed.

GitHub publication is **NOT ATTEMPTED**. The configured origin identifies the
established repository, but no external upload or workaround of prior approval/
security controls occurs. The local chain is preserved. Production deployment
requires a separate explicit approval after blockers are resolved; publication
would not authorize deployment.
